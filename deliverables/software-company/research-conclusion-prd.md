# PRD：IRIP 研究分析模块 — 推送结论栏功能

## 1. 项目信息

- **Language**: 中文
- **Programming Language**: React 18 + TypeScript + Ant Design 5 + TanStack Query + Zustand（复用现有前端技术栈）
- **Project Name**: `irip_research_conclusion_panel`
- **原始需求复述**：研究分析报告中的每个区块（echarts 图表、chart-ref 引用图表、data 结构化数据、Markdown 表格、文字结论）都需要"推送到右侧结论栏"的按钮；右侧结论栏类似 AI 助手的橱窗功能（ShowcasePanel），推送过去的图表和表格要正确渲染；用户在结论栏通过勾选多选栏目，点击"生成最终结论"后，将勾选栏目组装为最终结论，包含数据溯源信息（turn_id / run_id / 分析问题）及提炼出的结构化数据（metadata / points / series 三段式）。

---

## 2. 产品目标

1. **区块推送零摩擦**：用户在研究分析报告中可以一键将任意内容区块（图表、表格、结构化数据、文字结论）推送到右侧结论栏，无需手动复制粘贴，推送后的图表与表格保持正确渲染。
2. **结论可溯源、可结构化**：由勾选栏目组装生成的最终结论，必须携带完整的溯源链（来源 turn_id / run_id / 分析问题）和结构化数据快照（metadata / points / series），确保结论可信、可复核、可下游消费。
3. **与现有结论体系无缝衔接**：推送结论栏作为候选内容暂存与组装区，生成最终结论后沉淀进现有结论库（ConclusionLibrary）与产物体系（Insight / Dataset / View），不破坏已有的时间线、快照、版本化机制。

---

## 3. 用户故事

1. **作为研发工程师**，我希望在分析报告中每个图表和表格右上角都有"推送到结论栏"按钮，这样我可以把多个分析步骤产出的关键图表/表格收集到一起对比、取舍，而不是在长报告里反复滚动查找。

2. **作为研发工程师**，我希望推送过去到右侧结论栏的图表和表格能像原报告里一样正确渲染（ECharts 可交互、表格可滚动），这样我在结论栏里就能直接看清数据，不用回到原文确认。

3. **作为研发工程师**，我希望在右侧结论栏对每个条目进行勾选，并点击"生成最终结论"一次性把多个栏目组装成一条结论，这样我可以把分散的证据合成为一个完整结论。

4. **作为研发工程师**，我希望生成的最终结论自带数据溯源信息（来源轮次、run、分析问题）和结构化数据（meta/point/series），这样我的结论可被他人复核，也能被下游（报告导出、综合分析）直接消费。

5. **作为研发工程师**，我希望结论栏支持删除误推的条目、调整条目顺序，这样我可以像整理一个工作台一样维护候选内容，再决定哪些进入最终结论。

## 5. UI 交互设计

### 5.1 整体布局

复用 `WorkspaceDetail` 的三栏布局：
- **左栏**：AI 推荐 + 数据快照（不变）
- **中栏**：研究时间线（不变）；点击卡片弹出的"研究分析报告" Modal（TurnDetailPanel）是推送的发起端
- **右栏**：由现有"结论库"调整为"结论栏 + 结论库"的分区结构。结论栏（推送暂存 + 组装）在上，结论库（已沉淀结论，支持"用于下一轮"）在下，或以 Tab 切换。

> 说明：当前右栏已承载 ConclusionLibrary（已保存结论，可勾选"用于下一轮"）。新增的"结论栏"是推送暂存区，二者职责不同：结论栏 = 从报告推送来的候选内容（可组装最终结论）；结论库 = 已沉淀的结论（可被下一轮引用）。需在 UI 上明确区分，避免用户混淆（见待确认问题 Q1）。

### 5.2 推送交互流程

1. 用户在时间线点击某轮次卡片，弹出"研究分析报告" Modal（TurnDetailPanel）。
2. 报告以 Markdown 渲染，其中：
   - ` ```echarts ` 代码块 → ChartBlock 图表
   - ` ```chart-ref ` 代码块 → ChartRefBlock 图表
   - ` ```data ` / ` ```json ` 代码块 → StructuredDataBlock（含 metadata/points/series 折叠表格）
   - Markdown 表格 → GFM 表格
   - 候选结论文字 → 结论卡片
3. 每个可推送区块外层包一层"区块操作包装器"（参考 assistant 模块的 BlockWrapper），右上角悬停显示 **"推送到结论栏"** 按钮（icon + 文案）。
   - 悬停区块时按钮淡入显示；点击后调用推送接口，按钮变为 **"已推送"**（实心态），再次点击可从结论栏移除（幂等）。
   - 图表类区块：推送时保存 ECharts option JSON（echarts 块）或 chart-ref spec + 当前 sampleData 快照（chart-ref 块，因为 chart-ref 依赖 systemContext 动态取数，需在推送时把已构建的 option 一并落库，避免结论栏再次依赖运行时数据）。
   - 结构化数据块：推送时保存原始 JSON（metadata/points/series）。
   - Markdown 表格：推送时保存 Markdown 表格源文本。
   - 文字结论：推送时保存结论文本。
4. 推送成功后 toast 提示"已推送到结论栏"，右侧结论栏实时新增一张卡片。

### 5.3 右侧结论栏交互

1. **标题栏**：图标 + "结论栏" + 条目数量 Badge + 收起/展开按钮。
2. **筛选栏**（P1）：Segmented 切换 全部/图表/表格/数据/结论。
3. **条目卡片列表**（可滚动区）：
   - 每张卡片顶部：类型图标 + 可编辑标题 + 类型 Tag + 勾选框（Checkbox）。
   - 卡片中部：缩略预览（图表缩略图 / 表格前 3 行 / 结论前几行），复用 ShowcaseCard 的缩略渲染逻辑。
   - 卡片底部：溯源信息（来源轮次 #N · 分析问题摘要）+ 操作按钮（展开、定位原文、删除）。
   - 拖拽手柄用于排序（P1）。
4. **底部操作栏**：
   - "生成最终结论"主按钮：未勾选任何条目时禁用；勾选后高亮，显示已选数量。
   - 点击后弹出"生成最终结论"确认 Modal：
     - 预览组装后的结论结构（溯源块 + 结构化数据块）
     - 可编辑结论标题
     - 确认后调用生成接口，成功后 toast，刷新结论库，结论栏可按策略处理已用条目。

### 5.4 生成最终结论的数据组装

最终结论的 `statement` 采用结构化 JSON（兼容现有 ConclusionLibrary 的 `tryParseStructured` → `StructuredConclusionDisplay` 渲染逻辑），格式：

```
{
  "metadata": {                          // 元数据：溯源 + 概览
    "analysis_questions": ["问题1", "问题2"],   // 来源分析问题
    "source_turns": ["turn-id-1", "turn-id-2"], // 来源轮次
    "source_runs": ["run-id-1"],
    "generated_at": "2026-01-01T00:00:00Z",
    "summary": "用户可编辑的结论摘要"
  },
  "points": [                            // 数据点：聚合自勾选的结构化块/表格
    { "name": "峰值强度", "value": 1234.5, "unit": "a.u.", "描述": "..." }
  ],
  "series": [                            // 数据表：聚合自勾选的 series
    { "name": "拉曼光谱 BL-18", "columns": ["位移","强度"], "rows": [[100,0.1],...] }
  ]
}
```

- 勾选的图表类条目：从 chart-ref / echarts option 中提取 series 数据填入 `series`，提取关键标注填入 `points`。
- 勾选的结构化数据块：直接取其 metadata/points/series 合并。
- 勾选的 Markdown 表格：解析表头 + 行数据填入 `series`。
- 勾选的文字结论：其文本写入 `metadata.summary` 或单独拼接为结论正文。
- 溯源信息统一落入 `metadata`。
- 该结构化 statement 经现有 `POST /save-conclusion`（或新增生成接口）落库后，ConclusionLibrary 即可识别并以折叠表格展示。

### 5.5 状态管理

- 推送条目列表、勾选集合、排序、筛选等本地交互态用 Zustand store 管理（与现有结论库的 selectedRevisionIds 风格一致）。
- 推送/删除/排序等写操作用 TanStack Query mutation + 乐观更新（参考 ShowcasePanel 的 deleteMutation / renameMutation 模式）。
- 结论栏条目按 turn（轮次）维度查询；同一 Workspace 下跨轮次聚合属 P2。

## 6. 技术规范要点（供架构师参考）

- **可复用组件**：`ShowcasePanel` / `ShowcaseCard` / `BlockWrapper` 的交互模式（悬停操作、缩略图、展开 Modal、定位高亮、乐观更新）可直接迁移到研究模块，封装为 `ConclusionPanel` / `ConclusionDraftCard` / `ResearchBlockWrapper`。
- **图表渲染复用**：`ChartBlock`（echarts）、`ChartRefBlock`（chart-ref）、`StructuredDataBlock`（data）已具备渲染能力，结论栏缩略图与展开视图复用其渲染逻辑；chart-ref 推送时需将运行时构建好的 option 快照落库，结论栏按 echarts option 直接渲染。
- **后端**：现有 `POST /research/workspaces/{id}/turns/{turn_id}/save-conclusion` 接收 `{statement, block_type}`，可作为单个条目沉淀入口；"推送暂存"与"生成最终结论"需新增对应接口（见待确认 Q3）。结构化数据复用 PostgreSQL JSONB 存储。
- **溯源字段**：结论 / 暂存条目需新增 source_turn_id、source_run_id、question_text、block_index 等字段持久化。

## 7. 待确认问题

1. **结论栏与结论库的布局关系**：右栏当前已有"结论库"（已沉淀结论，可勾选"用于下一轮"）。新增"结论栏"（推送暂存 + 组装最终结论）后，二者是上下分区共存，还是用 Tab 切换？是否考虑把"生成最终结论"的结果也写入结论库（即结论栏是结论库的"草稿入口"）？
2. **推送条目的生命周期**：推送暂存的条目是否持久化到后端？还是仅前端会话级暂存、生成最终结论后即丢弃？（影响是否需要"暂存条目"表与增删改接口。）
3. **生成最终结论接口**：是复用现有 `save-conclusion`（单条 statement 落库）由前端组装好结构化 JSON 直接提交，还是后端提供专门的"批量组装"接口接收勾选条目 ID 列表并在服务端组装？（前者简单但溯源由前端拼装，后者更可靠。）
4. **图表溯源渲染**：chart-ref 推送时依赖运行时 systemContext 取数，若后续数据快照变化，结论栏中的图表是否需要锁定为推送时刻的数据快照？（建议锁定，需确认快照策略。）
5. **结论栏作用域**：结论栏是按当前选中轮次（turn）范围，还是整个 Workspace 范围（跨轮次聚合）？（P0 默认按 turn，P2 跨轮次，需确认优先级。）
6. **最终结论与产物体系关系**：生成最终结论后，是否默认同步创建 Insight 产物？还是保持纯结论库沉淀、产物确认仍走现有候选 accept 流程？（P2 已列为可选，需确认 P0 是否需要。）
