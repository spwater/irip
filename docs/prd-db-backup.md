# IRIP 数据库备份功能需求说明书

## 1. 项目信息

- **项目名称**: `irip-db-backup`
- **所属模块**: 平台治理（/governance）
- **语言**: 中文
- **技术栈**: 后端 Python/FastAPI/PostgreSQL 16/Celery，前端 React/Ant Design/TanStack Router
- **原始需求**: 在"平台治理"下新增"数据库备份"功能页面，包含两大功能——14天每日自动镜像+回滚、里程碑手动备份+恢复

### 1.1 现状基线

IRIP 已具备备份基础设施（V3-T03），本次在此基础上增量建设可视化备份管理：

| 已有能力 | 说明 |
|---------|------|
| `backup.py` | `pg_dump --format=custom` 导出 PG + `S3Repository` 导出 MinIO 对象，产出 `BackupManifest`（SHA-256 校验） |
| `backups.py` API | `POST/GET /api/v1/backups`、`POST /api/v1/backups/{id}/restore`，通过 Job 模型异步执行 |
| `restore.py` | `pg_restore` + MinIO 对象恢复 + 完整性校验 + 冒烟查询 |
| 权限 | `system:manage`（平台管理员） |
| 加密 | 可选 age 加密备份包 |

| 本次新增 | 说明 |
|---------|------|
| 每日自动快照 | Celery beat 定时触发，14天滚动保留 |
| 备份分类 | 区分"每日镜像"(daily) 与"里程碑备份"(milestone) |
| 里程碑元数据 | 名称 + 描述，不自动清理 |
| 前端管理页 | `/governance` 下新增"数据库备份" Tab，可视化管理两类备份 |

## 2. 产品目标

| 编号 | 目标 | 衡量标准 |
|------|------|---------|
| G1 | **数据安全底线**：保障平台数据可恢复，任何误操作或故障可在14天内回滚 | 每日快照连续14天无缺失；任意快照可在5分钟内完成恢复 |
| G2 | **里程碑可追溯**：关键节点（版本发布、大批量导入）有永久保留的恢复点 | 里程碑备份含名称+描述，不随时间自动清理，可随时恢复 |
| G3 | **操作可视化与安全可控**：管理员可在 UI 上直观查看、选择、确认回滚，避免误操作 | 列表展示日期/大小/状态；回滚前二次确认；仅平台管理员可操作 |

## 4. 功能需求

### 4.1 需求池

#### P0 — 必须完成

| 编号 | 标题 | 描述 |
|------|------|------|
| P0-01 | 每日自动快照 | Celery beat 每日凌晨定时触发 `pg_dump --format=custom` 数据库快照，备份类型标记为 `daily` |
| P0-02 | 14天滚动保留 | 每日快照仅保留最近14天，超过14天的 `daily` 类型快照自动清理（仅清理 daily，不清理 milestone） |
| P0-03 | 每日快照列表 | API + UI 展示最近14天每日快照列表，字段：备份ID、日期、文件大小、状态（成功/失败/进行中）、迁移版本 |
| P0-04 | 每日快照回滚 | 用户可在 UI 选择任意 daily 快照执行回滚（pg_restore），回滚前弹出危险操作确认对话框（需输入确认文本或二次点击） |
| P0-05 | 里程碑手动备份 | 用户可在 UI 手动创建里程碑备份，必填名称（≤100字符）和描述（≤500字符），备份类型标记为 `milestone` |
| P0-06 | 里程碑备份列表 | API + UI 展示里程碑备份列表，字段：名称、描述、创建时间、文件大小、状态、迁移版本 |
| P0-07 | 里程碑备份恢复 | 用户可选择任意里程碑备份执行恢复，恢复前弹出危险操作确认对话框 |
| P0-08 | 里程碑永久保留 | 里程碑备份不受14天自动清理策略影响，仅用户手动删除时才移除 |
| P0-09 | 管理员权限 | 所有备份查看、创建、回滚/恢复、删除操作均需 `platform_administrator` 权限（`system:manage`） |
| P0-10 | 治理页 Tab 入口 | 前端在 `/governance` 下新增"数据库备份" Tab，仅 `platform_administrator` 可见 |
| P0-11 | 回滚前自动备份 | 执行回滚/恢复前，系统自动创建一份当前状态的备份（类型 `pre_restore`），以便回滚操作本身可撤销 |

#### P1 — 重要

| 编号 | 标题 | 描述 |
|------|------|------|
| P1-01 | 快照状态实时刷新 | 备份/恢复进行中时，UI 显示进行中状态并自动轮询刷新（复用现有 Job 轮询机制） |
| P1-02 | 备份大小统计 | UI 顶部展示备份存储总用量、每日快照数量、里程碑备份数量等汇总信息 |
| P1-03 | 里程碑备份删除 | 用户可手动删除不再需要的里程碑备份，删除前需确认提示 |
| P1-04 | 备份失败告警 | 每日快照失败时，在 UI 列表中以红色状态标识，并在治理首页 SystemHealth 中反映 |
| P1-05 | 回滚操作审计 | 所有回滚/恢复操作写入审计日志（复用现有 audit 机制），记录操作人、目标快照、时间、结果 |

#### P2 — 后续

| 编号 | 标题 | 描述 |
|------|------|------|
| P2-01 | 备份下载 | 允许管理员从 UI 下载备份文件到本地（大文件需流式下载） |
| P2-02 | 备份加密 | 里程碑备份支持 age 加密（复用现有 age 加密能力） |
| P2-03 | 备份恢复演练 | 一键在隔离环境中执行恢复演练，验证备份可用性 |
| P2-04 | 可配置保留策略 | 允许管理员在 UI 配置每日快照保留天数（默认14天，可调整为7-30天） |

## 5. 数据模型变更

### 5.1 新增备份元数据表

复用现有 `Job` 模型（`kind` 区分类型），新增备份元数据表存储业务字段：

```sql
-- 备份元数据表（与 Job 关联）
CREATE TABLE backup_record (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  job_id UUID NOT NULL REFERENCES job(id) ON DELETE CASCADE,  -- 关联异步作业
  backup_type VARCHAR(20) NOT NULL,  -- daily / milestone / pre_restore
  name VARCHAR(100),                  -- 里程碑名称（daily 为 NULL）
  description VARCHAR(500),           -- 里程碑描述（daily 为 NULL）
  backup_date DATE,                   -- 快照日期（daily 用，便于按天列表）
  file_path TEXT NOT NULL,             -- 备份文件路径（挂载卷或 MinIO key）
  file_size BIGINT,                    -- 文件大小（字节）
  status VARCHAR(20) NOT NULL DEFAULT 'pending',  -- pending/running/succeeded/failed
  migration_version VARCHAR(100),     -- 备份时 Alembic 版本
  application_version VARCHAR(50),    -- 备份时应用版本
  created_by UUID REFERENCES app_user(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at TIMESTAMPTZ              -- 过期时间（daily=创建+14天，milestone=NULL）
);

CREATE INDEX idx_backup_record_type ON backup_record(backup_type);
CREATE INDEX idx_backup_record_date ON backup_record(backup_date);
CREATE INDEX idx_backup_record_expires ON backup_record(expires_at) WHERE expires_at IS NOT NULL;
```

### 5.2 Job payload 扩展

现有 Job payload 增加 `backup_type` 字段：
- `daily`：每日自动快照
- `milestone`：里程碑手动备份
- `pre_restore`：回滚前自动备份
- `restore`：恢复作业（不变）

## 6. 技术约束

| 约束 | 说明 |
|------|------|
| pg_dump 格式 | `--format=custom`（与现有 `backup.py` 一致） |
| 执行环境 | `pg_dump`/`pg_restore` 在 API 容器内执行（已装 postgresql-client-16） |
| 备份存储 | MinIO 或本地挂载卷（复用现有 `IRIP_BACKUP_OUTPUT_DIR` 配置） |
| 定时触发 | Celery beat 调度，每日凌晨（如 02:00）触发每日快照 |
| 自动清理 | Celery beat 定时任务（每日）扫描 `expires_at < now()` 的 `daily` 记录，清理文件 + 记录 |
| 完整性校验 | 复用现有 `BackupManifest` SHA-256 校验机制 |
| 权限 | `system:manage`（`platform_administrator`） |
| 前端路由 | `/governance` 内新增 Tab，非独立路由（复用 `GovernanceConsole` Tab 机制） |

## 7. 待确认问题

| 编号 | 问题 | 影响范围 | 建议倾向 |
|------|------|---------|---------|
| Q1 | 每日快照是否需要包含 MinIO 对象（完整备份），还是仅数据库快照？ | 备份大小、恢复完整性 | 建议仅数据库快照（体积小、恢复快）；MinIO 对象按需单独备份 |
| Q2 | 回滚/恢复操作是否需要停机（维护模式）？数据一致性如何保证？ | 用户体验、数据安全 | 建议回滚期间进入只读维护模式，禁止写操作，恢复后解除 |
| Q3 | 每日快照的执行时间窗口（02:00）是否会影响业务？ | 调度策略 | 建议 configurable，默认 02:00，可在系统配置中调整 |
| Q4 | 里程碑备份数量上限？是否需要设置存储配额？ | 存储管理 | 建议不设硬上限，由管理员手动管理；P2 可加配额告警 |
| Q5 | 回滚前自动备份（pre_restore）的保留策略？ | 存储管理 | 建议保留7天后自动清理，或随下次成功回滚后清理 |
| Q6 | 是否需要支持跨大版本回滚（备份迁移版本 > 当前代码版本）？ | 恢复能力 | 现有 restore.py 已拒绝自动降级迁移；建议保持，需人工处理 |
| Q7 | 备份文件存储位置（MinIO vs 本地卷）的选择策略？ | 部署灵活性 | 建议：单机部署用本地挂载卷，集群部署用 MinIO；由环境变量控制 |

## 8. 验收标准

| 编号 | 验收项 | 标准 |
|------|--------|------|
| AC-01 | 每日快照自动创建 | Celery beat 触发后5分钟内，backup_record 中出现一条 `daily` 类型、`succeeded` 状态的记录 |
| AC-02 | 14天滚动清理 | 第15天的快照在自动清理任务执行后被删除（文件+记录） |
| AC-03 | UI 列表展示 | 每日镜像 Tab 展示最近14天快照，里程碑 Tab 展示全部里程碑备份 |
| AC-04 | 回滚确认 | 点击回滚后弹出确认对话框，需输入确认文本方可执行 |
| AC-05 | 回滚前备份 | 执行回滚前自动创建 `pre_restore` 类型备份 |
| AC-06 | 里程碑创建 | 填写名称+描述后提交，5分钟内出现 `milestone` 类型、`succeeded` 状态记录 |
| AC-07 | 里程碑不清理 | 里程碑备份创建15天后仍存在 |
| AC-08 | 权限控制 | 非 `platform_administrator` 用户无法看到"数据库备份" Tab，API 返回 403 |
| AC-09 | 完整性校验 | 回滚前自动校验备份文件 SHA-256，不匹配则中止 |
