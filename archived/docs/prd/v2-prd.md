# IRIP Phase V2 产品需求文档（PRD）

## 1. 项目信息

- **Language:** 中文
- **Programming Language:** Python 3.12+（后端）、TypeScript + React 18（前端）
- **Project Name:** irip-platform
- **原始需求：** 基于《IRIP完整工程逐任务实施计划》中 Phase V2（任务 21–28），在 V1 粒度分析 L1→L3 全链路之上，构建版本化组件系统、流程引擎和篦冷机 ROM（Reduced Order Model）模型全生命周期，使平台具备"可插拔组件编排 + 代理模型管理 + 预测工作台"的完整能力。
- **范围：** V2 阶段增量需求，复用 V0 平台骨架（认证、权限、作业、工件、审计）与 V1 证据链（标准变量、事实、溯源、参数），不重写已有模块。
- **上游文档：** `docs/prd-v0.md`、`docs/prd-department.md`、`docs/arch-v0.md`、`docs/acceptance/v1-particle-size.md`

---

## 2. 产品目标

1. **建立版本化、可扩展的组件注册与执行体系**：通过 JSON Schema 验证的组件清单、不可变发布版本的组件注册表、以及统一的 Component Protocol（Python 运行时 + 命令行运行时），使数据摄入、映射转换、质量统计、模型预测等能力以可插拔、可沙箱化、可审计的方式接入平台，内置 29 个组件开箱即用。

2. **实现节点级可恢复的流程编排引擎**：支持版本化 FlowDefinition（DAG 校验：无环、端口类型匹配、参数 schema）、节点级调度（拓扑排序、子作业、输入/输出摘要），以及恢复（跳过已成功节点）、取消、重试机制，使研究员能将多个组件组装为端到端的数据处理与建模流水线。

3. **交付篦冷机 ROM 模型全生命周期管理**：从确定性数据集与示例 ROM 包出发，实现 ModelAdapter Protocol（load/validate_input/predict/healthcheck）、模型状态机（draft→pending_validation→validated→published→deprecated）、发布指针与回滚、适用域检查，以及 train/evaluate/applicability/predict 四个模型组件，使预测结果可写回 L2 model_execution 事实，并在前端预测工作台中完成交互式推理。

## 3. 用户故事

1. **As a** 平台管理员，**I want** 在组件管理页面查看已注册组件的清单、版本、运行时类型与状态，**so that** 我能掌握平台当前可用的处理能力全貌并管控组件发布。

2. **As a** 数据工程师，**I want** 选择数据摄入组件（Excel/CSV/JSON/PDF/PostgreSQL/REST/MinIO）并将读取的数据通过映射与转换组件（字段映射、单位转换、异常值检测等）处理为 ObservationTable，**so that** 外部异构数据能以标准化、可追溯的方式进入平台而不直接写事实。

3. **As a** 数据工程师，**I want** 将多个组件组装为流程（FlowDefinition），定义 DAG 拓扑与端口连接关系，并提交执行（FlowRun），**so that** 端到端的数据处理流水线可一次定义、重复运行、断点恢复。

4. **As a** 模型工程师，**I want** 基于篦冷机确定性数据集训练 ROM 模型，经过评估、适用域检查后发布，并在预测工作台中输入工况参数获得预测输出，**so that** 代理模型能为工业过程优化提供可追溯的量化预测。

5. **As a** 模型工程师，**I want** 在模型管理页面查看模型状态机流转、发布指针、回滚历史与适用域范围，**so that** 我能安全地管理模型版本并在发现问题时快速回退。

6. **As a** 研究员，**I want** 在预测工作台中选择已发布模型、输入参数并获取预测结果及置信区间，**so that** 无需编写代码即可使用模型进行工况分析。

## 6. 技术约束（与 V2 相关）

以下约束摘自实施计划 Global Constraints 及项目既有约定，V2 必须遵守：

1. **组件不可变性**：组件发布后版本不可变，修改需创建新版本，不覆盖已发布版本。
2. **组件安全**：组件执行需沙箱化，命令行组件在受限环境运行；网络访问受白名单/黑名单控制；PostgreSQL 组件仅允许 SELECT；REST 组件防 SSRF。
3. **流程确定性**：FlowRun 相同输入（组件版本 + 参数 + 输入数据快照）必须产生相同输出摘要（确定性可复现，与 V1 推导确定性原则一致）。
4. **模型可复现**：确定性数据集固定种子，模型训练/评估/预测可复现，模型包附带 SHA-256 校验。
5. **事实写入边界**：映射/转换组件产出 ObservationTable + DiagnosticReport，不直接写事实；只有 predict 组件将预测结果写为 L2 model_execution 事实（复用 V1 事实不可变修订机制）。
6. **权限继承**：组件执行与流程运行继承当前提交用户的对象权限（与 V0 安全规范一致）。
7. **审计**：模型状态机流转、发布指针变更、回滚操作均记录审计事件（仅追加，不可篡改）。
8. **权威存储**：PostgreSQL 为唯一权威存储；模型文件/数据集等大文件存 MinIO（SHA-256 内容寻址，复用 V0 工件服务）；Redis 仅作缓存/队列。

## 7. 待确认问题

1. **组件注册的权限模型**：哪些角色可以注册/发布组件？是否新增 `component:manage` 权限授予 platform_administrator 和 model_engineer？还是沿用 `standard:manage` 等现有权限？需确认。

2. **流程定义的权限模型**：哪些角色可以创建/编辑/执行流程？是否新增 `flow:manage` / `flow:execute` 权限？需确认。

3. **模型管理的权限模型**：模型状态机流转（特别是 published→deprecated 和回滚操作）需要哪些角色权限？是否新增 `model:manage` / `model:publish` 权限？审批分离是否适用（如训练者不能自己发布模型）？需确认。

4. **组件清单 manifest 格式标准**：YAML manifest 的具体字段结构是否需要在此 PRD 中固化，还是由架构师在设计中定义？当前 PRD 仅描述约束（kind/version/端口schema/参数schema/运行时声明），未固化字段名。需确认。

5. **命令行组件的沙箱化方案**：命令行运行时组件的沙箱化是通过 Docker 容器隔离、还是通过操作系统级限制（如 seccomp/namespace）？这影响部署复杂度和 V2 验收范围。需确认。

6. **预测结果写入事实的粒度**：predict 组件的每次预测是创建一条新的 model_execution 事实修订，还是按批次合并？预测频率高时事实表膨胀如何控制？需确认。

7. **模型适用域检查的判定标准**：适用域是简单的输入维度 min/max 边界检查，还是需要更复杂的域判定算法（如距离度量）？当前 PRD 假设为边界检查 + 越界标记不阻止预测。需确认。

8. **V2 验收门的具体路径**：V2 验收路径是否为"组件注册 → 组装流程执行数据摄入到统计 → 训练篦冷机模型 → 发布 → 预测工作台推理 → 预测事实溯源"？是否需要像 V1 一样定义核心不变量清单？需确认。

9. **内置组件的分组归类**：29 个内置组件在 ComponentsPage 中是按 kind 分组（ingestion/transform/quality/statistics/output/model）展示，还是统一平面列表？当前 PRD 默认按 kind 分组。需确认。

10. **流程可视化编辑器优先级**：拖拽式可视化流程编辑器（P2）是否在 V2 验收范围内？如果不在，流程定义通过何种方式创建（API / YAML / JSON）？当前 PRD 默认 V2 通过 API/YAML 定义，可视化编辑器为 P2。需确认。

---

> **V2 验收门：** 管理员可注册并发布组件；数据工程师可组装流程（含数据摄入→映射转换→质量统计），流程可执行、恢复、重试；模型工程师可训练篦冷机 ROM 模型、评估、发布并回滚；研究员可在预测工作台中基于已发布模型执行预测并获得可溯源的 model_execution 事实。
